# ResearchEvolve v0.3 — Semantic Research Explorer

v0.3 adds an optional semantic research layer on top of the deterministic v0.2 search kernel.

The design rule is simple:

> The Explorer proposes ideas. The evaluator decides truth.

An LLM, local model, heuristic program, or ChatGPT/Codex Skill can act as the Explorer. It never receives hidden evaluator internals and cannot directly mark a result as valid.

## Architecture

```text
ResearchSpec
    │
    ├── deterministic mutation ───────────────┐
    │                                         │
    └── Research Context                     │
             │                               │
             ▼                               │
      Explorer / LLM                         │
             │ structured proposals          │
             ▼                               │
        Idea Genome                          │
             │                               │
      semantic mutation / crossover          │
             │                               │
             └──────────── Candidate ◄────────┘
                              │
                              ▼
                       Evaluator Cascade
                              │
                ┌─────────────┼─────────────┐
                ▼             ▼             ▼
            MAP-Elites      Pareto        Novelty
                │             │             │
                └─────────────┼─────────────┘
                              ▼
                      Research Graph
                              │
                              ▼
                         IdeaMemory
                              │
                              └──── feedback to next Explorer call
```

## 1. Enable the Explorer

Add this to a `ResearchSpec`:

```json
{
  "explorer": {
    "enabled": true,
    "interval": 1,
    "proposals_per_interval": 2,
    "context_candidates": 8,
    "feedback_items": 12,
    "timeout_seconds": 60
  }
}
```

- `interval`: call the Explorer every N generations.
- `proposals_per_interval`: maximum semantic proposals evaluated per call.
- `context_candidates`: maximum candidate summaries exposed to the Explorer.
- `feedback_items`: recent proposal outcomes returned as research memory.
- `timeout_seconds`: external Explorer command timeout.

## 2. Explorer command protocol

Run ResearchEvolve with an external Explorer command:

```bash
research-evolve run \
  --spec research.json \
  --evaluator evaluator.py \
  --seeds seeds.json \
  --explorer-command "python my_explorer.py" \
  --workspace .researchevolve/my-run
```

The command reads one JSON request from stdin and writes one JSON response to stdout.

### Request

```json
{
  "schema_version": 1,
  "count": 2,
  "context": {
    "problem": "...",
    "generation": 4,
    "objectives": [],
    "constraints": [],
    "candidates": [],
    "pareto": [],
    "feedback": [],
    "metadata": {}
  },
  "response_contract": {}
}
```

Candidate summaries contain:

- candidate id
- payload
- score
- domain metrics
- behavior features
- novelty score
- Idea Genome when the candidate came from a prior semantic proposal

The `feedback` list contains previous proposals and their evaluator outcomes, allowing the next Explorer call to learn from failed and successful ideas.

## 3. Semantic mutation proposal

```json
{
  "proposals": [
    {
      "kind": "semantic_mutation",
      "parent_ids": ["candidate-id"],
      "patch": {
        "set": {
          "representation": "polynomial",
          "lift": 31
        },
        "delete": [],
        "append": {
          "generators_a": [7]
        }
      },
      "genome": {
        "representation": "polynomial",
        "construction": "cyclic lifted construction",
        "mechanisms": ["increase algebraic symmetry"],
        "invariants": ["CSS commutation must remain testable"],
        "assumptions": ["cyclic symmetry may improve structured search"],
        "tags": ["qldpc", "algebraic"],
        "traits": {
          "symmetry": "cyclic"
        },
        "notes": "Test a representation-level change rather than a local parameter edit."
      },
      "rationale": "Try a more algebraically structured representation.",
      "expected_effects": {
        "distance": "possibly increase",
        "search_diversity": "increase"
      },
      "confidence": 0.62,
      "metadata": {
        "provider": "your-provider",
        "model": "your-model"
      }
    }
  ]
}
```

The Explorer does **not** submit arbitrary executable code. `SemanticPatch` currently supports auditable top-level operations only:

- `set`
- `delete`
- `append`

The resulting candidate still passes through the normal evaluator cascade.

## 4. Semantic crossover proposal

A crossover has exactly two parents:

```json
{
  "kind": "semantic_crossover",
  "parent_ids": ["parent-a", "parent-b"],
  "inherit_from_secondary": [
    "representation",
    "generators_b"
  ],
  "patch": {
    "set": {
      "lift": 37
    },
    "delete": [],
    "append": {}
  },
  "genome": {
    "representation": "group algebra",
    "construction": "hybrid of two archived ideas",
    "mechanisms": ["semantic recombination"],
    "tags": ["crossover"]
  },
  "rationale": "Combine parent A's construction with parent B's representation.",
  "confidence": 0.55
}
```

ResearchEvolve starts from parent A, copies only the named top-level fields from parent B, then applies the semantic patch. This keeps crossover deterministic and auditable.

## 5. Idea Genome

`IdeaGenome` is deliberately separate from raw code or candidate parameters. It records the research concept behind a proposal:

```text
representation
construction
mechanisms
invariants
assumptions
tags
traits
notes
```

The goal is to make future versions able to perform semantic retrieval and crossover over *ideas*, not only over code strings.

## 6. Research memory

v0.3 creates another persistent artifact:

```text
.researchevolve/<run>/ideas.sqlite3
```

It records:

- Idea Genomes
- proposal kind
- parent lineage
- rationale
- expected effects
- confidence
- provider/model metadata supplied by the Explorer
- realized candidate id
- validity
- score
- accepted/rejected/invalid status

Inspect it with:

```bash
research-evolve ideas --workspace .researchevolve/my-run
research-evolve proposals --workspace .researchevolve/my-run
```

The same relationships are mirrored into the Research Graph:

```text
Candidate A ──inspired────┐
                          ▼
Idea ──proposed_as──► Proposal ──realized_as──► Candidate C
                                              │
                                              └──expresses──► Idea
```

## 7. Failure isolation

Explorer failures are intentionally non-fatal.

If the external command times out, crashes, returns invalid JSON, hallucinates an unavailable parent id, or produces a patch that cannot be applied:

- the deterministic evolutionary search continues;
- the error/proposal is recorded;
- no candidate is treated as valid without evaluator approval.

This separation is important for research-grade use.

## 8. Reproducibility

`manifest.json` now includes an Explorer identity fingerprint. Raw structured proposals and evaluator outcomes are persisted in `ideas.sqlite3`.

External LLM sampling can still be nondeterministic, so v0.3 does **not** claim bit-for-bit reproducibility of LLM-generated proposals. Instead it provides an auditable record of exactly which proposals were evaluated and what happened to them.

## 9. Run the semantic42 demo

The repository includes a deterministic protocol demo that behaves like an Explorer without requiring an API key:

```bash
research-evolve run \
  --spec examples/semantic42/spec.json \
  --evaluator examples/target42/evaluator.py \
  --seeds examples/semantic42/seeds.json \
  --explorer-command "python examples/semantic42/explorer.py" \
  --workspace .researchevolve/semantic42 \
  --islands 2
```

Then inspect:

```bash
research-evolve ideas --workspace .researchevolve/semantic42
research-evolve proposals --workspace .researchevolve/semantic42
research-evolve graph --workspace .researchevolve/semantic42 --output semantic42-graph.json
```

## 10. Connecting a real LLM

ResearchEvolve intentionally does not hard-code a vendor SDK in v0.3. Write a thin wrapper process that:

1. reads the ResearchEvolve JSON request;
2. converts the context into your model prompt;
3. asks the model for the exact proposal schema;
4. validates/parses the model response;
5. writes `{ "proposals": [...] }` to stdout.

That wrapper can use OpenAI, Claude, Gemini, Qwen, DeepSeek, a local model, or a future ChatGPT/Codex Skill. The search/evaluation engine remains unchanged.

## v0.3 boundary

v0.3 provides semantic proposal generation and structured research memory. It does not yet implement:

- autonomous literature retrieval
- conjecture extraction from numerical observations
- dedicated counterexample agents
- proof planning/proving
- Lean/Rocq formalization

Those belong to the next research loops rather than the search kernel itself.
