# ResearchEvolve v0.5 — Proof Pipeline

v0.5 adds a proof-oriented stage after the v0.4 empirical discovery loop:

```text
Empirically Supported Conjecture
              │
              ▼
         Proof Preflight
   scan all evaluated candidates
              │
       counterexample?
        ┌─────┴─────┐
       yes          no
        │            │
        ▼            ▼
     Refuted      ProofSpec
                      │
                      ▼
                 Proof Planner
                      │
                      ▼
                  Lemma DAG
                      │
                      ▼
                    Prover
                      │
                      ▼
                Proof Artifact
                      │
                      ▼
          Independent Adversarial
                  Verifier
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       rejected   inconclusive  verified
                                  │
                                  ▼
                    verified_natural_language
```

The proof stage is deliberately separate from `research-evolve run`. It consumes a completed research workspace and writes its own:

```text
proofs.sqlite3
proof_manifest.json
proof_summary.json
```

This separation prevents proof-model nondeterminism from changing evolutionary checkpoint semantics or the source research manifest.

---

## 1. ProofSpec freezes the target

A `ProofSpec` is constructed from an `empirically_supported` v0.4 `Conjecture`.

It records:

- exact conjecture ID;
- exact natural-language statement;
- exact machine-testable predicate;
- explicit hard assumptions derived from the source `ResearchSpec` constraints;
- empirical evidence candidate IDs;
- source generation and metadata.

The planner and prover receive this frozen object. They are not allowed to silently weaken the theorem, change quantifiers, or add hidden assumptions.

---

## 2. Proof preflight

Before invoking any proof model, v0.5 re-evaluates the conjecture predicate against **every valid candidate already stored in `candidates.sqlite3`**.

If an existing candidate violates the conjecture:

1. the candidate is recorded as a v0.4 `Counterexample` with source `proof_preflight`;
2. the conjecture is changed to `refuted`;
3. Research Graph receives the new counterexample relation;
4. no planner or prover is called.

This avoids spending proof budget on a statement that the experiment database already disproves.

The preflight does not run new candidates or new evaluator jobs. Active counterexample search remains the responsibility of the v0.4 discovery loop.

---

## 3. ProofPlan and Lemma DAG

The planner emits:

```json
{
  "strategy": "...",
  "lemmas": [
    {
      "label": "lemma-a",
      "statement": "...",
      "depends_on": [],
      "role": "supporting"
    },
    {
      "label": "lemma-b",
      "statement": "...",
      "depends_on": ["lemma-a"],
      "role": "final"
    }
  ]
}
```

ResearchEvolve validates the plan deterministically:

- labels must be non-empty and unique;
- statements must be non-empty;
- dependencies must reference existing labels;
- self-dependency is forbidden;
- cycles are forbidden;
- the number of lemmas is bounded by `--max-lemmas`.

The corresponding Research Graph becomes:

```text
ProofPlan
   ├── decomposes_into → Lemma A
   ├── decomposes_into → Lemma B
   └── decomposes_into → Lemma C

Lemma C ── depends_on → Lemma A
Lemma C ── depends_on → Lemma B
```

---

## 4. ProofArtifact

The prover must return one argument for every planned lemma plus one final argument:

```json
{
  "lemma_arguments": {
    "lemma-a": "...",
    "lemma-b": "..."
  },
  "final_argument": "...",
  "assumptions_used": []
}
```

ResearchEvolve rejects the artifact before verification if:

- a planned lemma argument is missing;
- an unknown lemma label is added;
- a lemma argument is empty;
- `final_argument` is empty;
- the artifact declares assumptions not present in the frozen `ProofSpec`.

This catches structural failures without asking the verifier to compensate for malformed output.

---

## 5. Independent adversarial verifier

The verifier receives:

- the original `ProofSpec`;
- the `ProofPlan`;
- the complete `ProofArtifact`;
- empirical evidence only as context;
- explicit instructions to attack the argument.

It returns:

```json
{
  "decision": "verified",
  "issues": [],
  "confidence": 0.93,
  "adversarial_notes": "..."
}
```

Possible decisions:

```text
verified
rejected
inconclusive
```

Issues have severities:

```text
error
warning
note
```

ResearchEvolve then applies a deterministic gate:

```text
verifier says rejected
    → rejected

verifier reports any error
    → rejected

verifier says verified
AND confidence >= threshold
AND no error issues
    → verified_natural_language

otherwise
    → inconclusive
```

The external model therefore cannot return `verified` while simultaneously describing a fatal logical gap and still pass the pipeline.

---

## 6. Prover / Verifier separation

For command adapters, ResearchEvolve fingerprints the underlying command and referenced script contents without including the actor role.

Therefore:

```text
python same_script.py  as Prover
python same_script.py  as Verifier
```

has the same implementation identity and is rejected.

The planner may share an implementation with the prover in v0.5, but the verifier must be independent from the prover.

For serious deployments, use genuinely different workers/models/configurations rather than merely different files containing identical logic.

---

## 7. Status semantics

v0.5 intentionally does **not** introduce a generic `proved` status.

The strongest current proof status is:

```text
verified_natural_language
```

It means:

> A structured natural-language proof artifact passed structural checks and was accepted by an independent adversarial verifier under the configured threshold.

It does **not** mean:

```text
Lean checked
Coq checked
Isabelle checked
SMT certified
kernel verified
formally proved
```

Formal proof objects should receive a separate status in a later release.

---

## 8. Persistence

A proof workspace adds:

```text
.researchevolve/run/
├── candidates.sqlite3
├── ideas.sqlite3
├── conjectures.sqlite3
├── proofs.sqlite3
├── research_graph.sqlite3
├── manifest.json
├── proof_manifest.json
├── summary.json
└── proof_summary.json
```

`proofs.sqlite3` stores four journals:

```text
proof_specs
proof_plans
proof_artifacts
proof_reviews
```

Each stage has an internal ResearchEvolve-generated ID. External command outputs do not choose graph IDs.

---

## 9. Proof manifest

`proof_manifest.json` fingerprints:

- source research-run fingerprint;
- planner implementation identity;
- prover implementation identity;
- verifier implementation identity;
- maximum conjectures;
- maximum lemmas;
- evidence-context size;
- verifier confidence threshold.

If the same workspace is later used with a different proof configuration, ResearchEvolve refuses to silently mix the new proof run with the previous proof journal.

# CLI

First run research/conjecture discovery. For example:

```bash
research-evolve run \
  --spec examples/conjecture42/spec.json \
  --evaluator examples/target42/evaluator.py \
  --seeds examples/conjecture42/seeds.json \
  --conjecturer-command "python examples/conjecture42/conjecturer.py" \
  --workspace .researchevolve/proof42 \
  --islands 2
```

Then run the proof pipeline:

```bash
research-evolve prove \
  --workspace .researchevolve/proof42 \
  --planner-command "python examples/proof42/planner.py" \
  --prover-command "python examples/proof42/prover.py" \
  --verifier-command "python examples/proof42/verifier.py" \
  --max-conjectures 4 \
  --max-lemmas 24 \
  --min-verifier-confidence 0.7
```

Inspect proof state:

```bash
research-evolve proof-specs --workspace .researchevolve/proof42
research-evolve proof-plans --workspace .researchevolve/proof42
research-evolve proof-artifacts --workspace .researchevolve/proof42
research-evolve proof-reviews --workspace .researchevolve/proof42
research-evolve proof-manifest --workspace .researchevolve/proof42
```

Export the full Research Graph:

```bash
research-evolve graph \
  --workspace .researchevolve/proof42 \
  --output proof42-graph.json
```

# Research Graph additions

v0.5 adds:

```text
ProofSpec
ProofPlan
Lemma
ProofArtifact
ProofReview
ProofActorError
```

Typical lineage:

```text
Conjecture
    ▲
    │ targets_conjecture
ProofSpec
    ▲
    │ plans_for
ProofPlan
    │
    ├── decomposes_into → Lemma A
    ├── decomposes_into → Lemma B
    └── decomposes_into → Lemma C

ProofArtifact
    ├── implements_plan → ProofPlan
    └── claims_proof_of → ProofSpec

ProofReview
    ├── reviews → ProofArtifact
    └── supports_natural_language_proof_of → Conjecture
```

The relation is deliberately named `claims_proof_of`; ResearchEvolve does not treat an unverified artifact as a theorem.

---

# What v0.5 still does not do

v0.5 does not yet provide:

- Lean/Coq/Isabelle compilation;
- automatic theorem formalization;
- proof-assistant kernel checking;
- citation-grounded literature lemmas;
- multi-verifier quorum;
- theorem-library retrieval;
- symbolic algebra verification beyond the domain evaluator;
- proof repair loops after verifier feedback.

Those are natural candidates for later releases.

A reasonable next milestone is **v0.6 formal verification / proof repair**:

```text
Natural-language proof
        ↓
Formalizer
        ↓
Lean theorem / lemmas
        ↓
Kernel check
        ↓
compiler errors / unsolved goals
        ↓
Proof Repair
        ↓
formal_verified
```
