# ResearchEvolve v0.6 — Lean Formal Verification

v0.6 adds a third truth layer after empirical discovery and independent natural-language proof review:

```text
empirically_supported
        ↓
verified_natural_language
        ↓
FormalizationSpec
        ↓
Formalizer
        ↓
Lean proof term
        ↓
LeanKernel
   ┌────┴─────┐
 failure    success
   │            │
   ▼            ▼
 diagnostics   axiom audit
   │            │
   ▼            ▼
 Repairer   formal_verified
   │
   └──────────► LeanKernel
```

The core v0.6 principle is simple:

> **A model may propose Lean proof text, but only the configured Lean process may grant `formal_verified`.**

---

## 1. Truth ladder

ResearchEvolve intentionally keeps these states separate:

```text
Idea / candidate
        ↓
independent evaluator
        ↓
empirical observations
        ↓
empirically_supported conjecture
        ↓
independent natural-language proof review
        ↓
verified_natural_language
        ↓
Lean target + proof term
        ↓
Lean compiler/kernel + axiom audit
        ↓
formal_verified
```

`formal_verified` is stronger than `verified_natural_language`, but it is still relative to the exact theorem encoded in Lean. A poor informal-to-formal translation can faithfully prove the wrong theorem, which is why v0.6 freezes the formal contract before asking a model for a proof term.

---

## 2. Formal contracts are research inputs

The formal target is supplied in `ResearchSpec.metadata.formal_contracts`.

Example:

```json
{
  "metadata": {
    "formal_contracts": [
      {
        "conjecture_statement": "Distance to 42 is always non-negative for evaluated candidates.",
        "backend": "lean4",
        "toolchain": "leanprover/lean4:v4.30.0",
        "theorem_name": "distance_to_42_nonnegative",
        "theorem_signature": "theorem distance_to_42_nonnegative (x : Int) : 0 ≤ Int.natAbs (x - 42)",
        "imports": [],
        "preamble": "",
        "metadata": {
          "semantic_mapping": "Evaluated integer x maps to Lean Int; abs(x-42) maps to Int.natAbs (x-42)."
        }
      }
    ]
  }
}
```

A contract is matched by the exact `conjecture_statement`. v0.6 deliberately refuses to let the Formalizer invent a target when no matching contract exists.

### Why freeze the theorem signature?

Without a frozen target, a model could receive:

```text
For every x, P(x)
```

and emit an easier theorem such as:

```lean
theorem weakened (x : Nat) (h : P x) : P x := h
```

Lean would correctly verify the weaker theorem, but ResearchEvolve would have proven the wrong claim.

Therefore the model never owns:

- theorem name;
- theorem binders;
- assumptions;
- conclusion;
- imports;
- trusted definitions;
- toolchain.

It only owns the theorem body.

---

## 3. Frozen `preamble`

Sometimes a theorem refers to a project-specific mathematical object or definition. That definition must not be invented by the Formalizer.

Use the contract `preamble` for trusted Lean declarations:

```json
{
  "preamble": "def distanceTo42 (x : Int) : Nat := Int.natAbs (x - 42)",
  "theorem_signature": "theorem distanceTo42_nonnegative (x : Int) : 0 ≤ distanceTo42 x"
}
```

The generated source then has the structure:

```lean
-- frozen imports
import ...

-- frozen trusted preamble
def distanceTo42 ... := ...

-- model controls only this proof body
theorem distanceTo42_nonnegative ... := by
  ...

#print axioms distanceTo42_nonnegative
```

This prevents a model from redefining the object being proved about.

---

## 4. Why v0.6 forbids top-level model helpers

The protocol still carries a `helper_source` field for forward compatibility, but the v0.6 kernel gate requires it to be empty.

A model may use local proof structure:

```lean
by
  have h₁ : ... := ...
  have h₂ : ... := ...
  exact ...
```

but may not add arbitrary declarations before the theorem.

This is intentional. Top-level declarations can affect name resolution, notation, syntax, namespaces, instances, or theorem meaning. Trusted global helpers should be placed in the frozen `preamble` or a pinned imported library.

---

## 5. Source gate

Before Lean is invoked, `LeanKernel` rejects a conservative set of escape hatches / metaprogramming surfaces in generated source:

```text
sorry
admit
axiom
unsafe
extern
opaque
run_tac
elab
macro
syntax
#eval
#run
```

This is defense in depth, not a replacement for Lean checking.

The gate also rejects a non-empty model-supplied `helper_source`.

---

## 6. Toolchain pinning

Each formal contract freezes a toolchain, for example:

```text
leanprover/lean4:v4.30.0
```

Before checking the theorem, ResearchEvolve runs:

```bash
lean --version
```

and compares the detected version with the frozen contract.

A mismatch yields:

```text
environment_error
```

not `kernel_rejected`, because the theorem has not been tested in the requested environment.

The repository also includes:

```text
lean-toolchain
```

so Elan-based environments select the pinned integration-test toolchain.

---

## 7. Kernel result gate

The Lean process must satisfy all of the following:

```text
source gate accepted
AND
Lean version == frozen toolchain version
AND
Lean exit code == 0
AND
no parsed Lean error diagnostics
AND
#print axioms output is parseable
AND
all theorem axiom dependencies are allowed
```

Only then:

```text
formal_verified
```

A model output can never directly set this state.

---

## 8. Axiom audit

ResearchEvolve appends:

```lean
#print axioms theoremName
```

to every generated formal artifact.

The default v0.6 allowlist is:

```text
propext
Classical.choice
Quot.sound
```

These are Lean's standard logical axioms. A theorem depending on other axioms is rejected by the default gate.

Examples blocked by default:

```text
sorryAx
Lean.trustCompiler
Custom.myAxiom
```

A successful Lean exit is therefore not enough by itself.

---

## 9. Repair loop

A failed Lean attempt produces a structured `KernelResult`:

```json
{
  "passed": false,
  "status": "kernel_rejected",
  "detected_version": "4.30.0",
  "exit_code": 1,
  "diagnostics": [
    {
      "severity": "error",
      "line": 3,
      "column": 8,
      "message": "..."
    }
  ],
  "gate_reason": "lean-exit-nonzero"
}
```

If a Repairer is configured and the repair budget remains, ResearchEvolve sends it:

```text
Frozen FormalizationSpec
Previous FormalArtifact
KernelResult
Previous kernel history
```

The Repairer may only replace the proof term. It cannot change imports, preamble, theorem signature, theorem name, or toolchain.

Lineage:

```text
FormalArtifact #0
      │
      ├── KernelResult #0 (failed)
      │
      └── repaired_into
             ▼
       FormalArtifact #1
             │
             └── KernelResult #1 (formal_verified)
```

If the repair budget is exhausted:

```text
repair_exhausted
```

If Lean cannot be run in the frozen environment:

```text
environment_error
```

## 10. Persistence

A v0.6 workspace may contain:

```text
.researchevolve/run/
├── candidates.sqlite3
├── ideas.sqlite3
├── conjectures.sqlite3
├── proofs.sqlite3
├── formal.sqlite3
├── research_graph.sqlite3
├── checkpoint.json
├── manifest.json
├── proof_manifest.json
├── formal_manifest.json
├── summary.json
├── proof_summary.json
├── formal_summary.json
└── formal_sources/
    ├── formal-artifact-....lean
    └── formal-artifact-....lean
```

`formal.sqlite3` contains:

```text
formal_specs
formal_artifacts
kernel_runs
```

The exact Lean source is stored both in the formal journal and as an inspectable `.lean` artifact. A SHA-256 of each source is recorded with the artifact/kernel result.

---

## 11. Formal manifest

`formal_manifest.json` is separate from the research and natural-language proof manifests.

It binds the formal run to:

- source research fingerprint;
- source generation;
- proof manifest fingerprint;
- Formalizer identity;
- Repairer identity;
- Lean kernel command identity;
- target / repair / evidence budgets;
- hash of all frozen formal contracts.

This prevents silently mixing results produced under different theorem mappings or kernel policies.

---

## 12. Stale formal verification

A formal theorem is not allowed to remain an active certificate if the upstream research lineage becomes stale.

Suppose:

```text
Conjecture A
  → verified_natural_language
  → formal_verified
```

and a later evaluated candidate refutes Conjecture A. v0.5 invalidates the natural-language proof lineage. On the next v0.6 pass, ResearchEvolve marks the corresponding formal records:

```text
FormalizationSpec → invalidated
FormalArtifact     → invalidated
KernelResult       → invalidated
```

The historical Lean result remains in the journal for audit, but `passed=false` is set on the active record and the historical status is preserved in payload metadata.

This distinction matters: a kernel may have correctly proved a Lean theorem at time T, while the mapping between that theorem and the current empirical research claim has later become invalid.

After the research and v0.5 proof phases:

```bash
research-evolve formalize \
  --workspace .researchevolve/run \
  --formalizer-command "python formalizer.py" \
  --repairer-command "python repairer.py" \
  --lean-command lean \
  --max-targets 4 \
  --max-repairs 2
```

```bash
research-evolve formal-specs --workspace .researchevolve/run
research-evolve formal-artifacts --workspace .researchevolve/run
research-evolve kernel-runs --workspace .researchevolve/run
```

## 14. `formal42` integration demo

The repository contains a deterministic no-API-key demo:

```text
examples/formal42/
├── spec.json
├── seeds.json
├── formalizer.py
└── repairer.py
```

The full pipeline is:

```bash
research-evolve run \
  --spec examples/formal42/spec.json \
  --evaluator examples/target42/evaluator.py \
  --seeds examples/formal42/seeds.json \
  --conjecturer-command "python examples/conjecture42/conjecturer.py" \
  --workspace .researchevolve/formal42 \
  --islands 2

research-evolve prove \
  --workspace .researchevolve/formal42 \
  --planner-command "python examples/proof42/planner.py" \
  --prover-command "python examples/proof42/prover.py" \
  --verifier-command "python examples/proof42/verifier.py"

research-evolve formalize \
  --workspace .researchevolve/formal42 \
  --formalizer-command "python examples/formal42/formalizer.py" \
  --repairer-command "python examples/formal42/repairer.py" \
  --lean-command lean
```

The demo Formalizer intentionally emits an ill-typed first proof term. The real Lean process must reject it. The Repairer then replaces it with a valid term and the second kernel run should produce `formal_verified`.

## 15. Security limitation

Lean elaboration/tactics are executable computation. The v0.6 source gate reduces the attack surface but does **not** make the local subprocess a hardened sandbox.

For autonomous/untrusted Formalizers, run Lean in an isolated container/VM/remote worker with limited filesystem, CPU, memory, processes, wall time, and network access. Do not expose provider secrets or evaluator/grader internals to that worker.

See [`../SECURITY.md`](../SECURITY.md).

---

## 16. What v0.6 does not claim

v0.6 does **not** automatically solve informal-to-formal translation. The researcher still has to provide an auditable `formal_contracts` mapping.

It also does not yet provide:

- Mathlib project/environment management for arbitrary imports;
- theorem retrieval from a large formal library;
- formal lemma search / premise selection;
- multiple proof-assistant backends;
- distributed Lean workers;
- proof-term minimization;
- certificate signing / attestation.

Those are natural candidates for later versions.

## 17. Toward qLDPC formalization

For qLDPC, a future domain contract can progressively formalize claims such as:

```text
circulant construction definition
        ↓
Hx / Hz dimensions
        ↓
CSS commutation Hx * Hzᵀ = 0
        ↓
rank-derived k identity
        ↓
family-specific algebraic lemmas
```

The important v0.6 contribution is not that all qLDPC mathematics is already formalized. It is that ResearchEvolve now has an auditable path from:

```text
empirical discovery
→ conjecture
→ natural-language proof
→ frozen formal statement
→ real proof kernel
```

without allowing the same generative model to award itself the final truth status.
