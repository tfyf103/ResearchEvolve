# ResearchEvolve v0.6 — Lean Formal Verification

v0.6 adds a third truth layer after empirical discovery and independent natural-language proof review:

```text
empirically_supported
        ↓
verified_natural_language
        ↓
FormalizationSpec
        ↓
Formalizer
        ↓
Lean proof term
        ↓
LeanKernel
   ┌────┴─────┐
 failure    success
   │            │
   ▼            ▼
 diagnostics   axiom audit
   │            │
   ▼            ▼
 Repairer   formal_verified
   │
   └──────────► LeanKernel
```

> **A model may propose a Lean theorem body, but only the configured Lean gate may grant `formal_verified`.**

---

## 1. Truth ladder

```text
Candidate
   ↓ independent evaluator
Empirical evidence
   ↓
empirically_supported
   ↓ independent NL proof review
verified_natural_language
   ↓ frozen informal→formal mapping
FormalizationSpec
   ↓ generated proof term
Lean compiler/kernel
   ↓ axiom audit
formal_verified
```

`formal_verified` is relative to the exact Lean theorem being checked. A formally correct proof of the wrong formalization is still the wrong research result, so v0.6 makes the mapping itself an explicit research input.

---

## 2. Formal contract = statement + machine predicate + Lean theorem

A contract lives in:

```text
ResearchSpec.metadata.formal_contracts
```

Example:

```json
{
  "metadata": {
    "formal_contracts": [
      {
        "conjecture_statement": "Distance to 42 is always non-negative for evaluated candidates.",
        "conjecture_predicate": {
          "left": {"source": "metrics", "key": "distance_to_42"},
          "operator": "ge",
          "right_constant": 0
        },
        "backend": "lean4",
        "toolchain": "leanprover/lean4:v4.30.0",
        "theorem_name": "distance_to_42_nonnegative",
        "theorem_signature": "theorem distance_to_42_nonnegative (x : Int) : 0 ≤ Int.natAbs (x - 42)",
        "imports": [],
        "preamble": "",
        "metadata": {
          "semantic_mapping": "Explain why this Lean theorem represents the v0.4 predicate."
        }
      }
    ]
  }
}
```

ResearchEvolve normalizes the v0.4 `Predicate` and matches a contract using both:

```text
exact conjecture statement
+
normalized machine predicate
```

This prevents two conjectures with identical prose but different executable semantics from silently sharing one Lean target.

If no exact contract exists:

```text
missing_contract
```

The Formalizer is never asked to invent a theorem signature.

---

## 3. Frozen theorem target

The model does **not** control:

- `conjecture_statement`;
- `conjecture_predicate`;
- Lean backend;
- Lean toolchain;
- imports;
- trusted preamble declarations;
- theorem name;
- theorem binders;
- assumptions;
- theorem conclusion.

`theorem_signature` must start with `theorem` or `lemma`, contain the configured theorem name, and must **not** contain `:=`.

The generated actor controls only the theorem body:

```lean
by
  ...
```

Without this boundary, a model could replace a difficult theorem by a weaker theorem that Lean correctly proves.

---

## 4. Trusted frozen `preamble`

Project-specific definitions belong in the contract:

```json
{
  "preamble": "def distanceTo42 (x : Int) : Nat := Int.natAbs (x - 42)",
  "theorem_signature": "theorem distanceTo42_nonnegative (x : Int) : 0 ≤ distanceTo42 x"
}
```

The final source shape is:

```lean
-- frozen imports
import ...

-- frozen trusted definitions
def distanceTo42 ... := ...

-- frozen theorem declaration + generated body
theorem distanceTo42_nonnegative ... := by
  ...

#print axioms distanceTo42_nonnegative
```

The Formalizer cannot redefine `distanceTo42` to make the theorem trivial.

---

## 5. Why top-level generated helpers are disabled

v0.6 rejects non-empty model-supplied `helper_source`.

A model may use local proof steps:

```lean
by
  have h₁ : ... := ...
  have h₂ : ... := ...
  exact ...
```

but may not inject arbitrary global declarations before the frozen theorem. Global declarations can alter notation, instances, namespaces, name resolution, or parsing and therefore expand the informal→formal trust surface.

Trusted global helpers belong in the frozen preamble or a pinned imported library.

---

## 6. Conservative source gate

Before Lean is run, v0.6 rejects generated source containing:

```text
sorry
admit
axiom
unsafe
extern
opaque
run_tac
elab
macro
syntax
#eval
#run
```

This is intentionally conservative defense in depth. It does **not** turn arbitrary Lean code into a safe sandbox.

---

## 7. Toolchain pinning

Each contract freezes a Lean toolchain, for example:

```text
leanprover/lean4:v4.30.0
```

For both version detection and theorem compilation, ResearchEvolve creates a temporary directory and writes:

```text
lean-toolchain
```

containing the frozen contract value. Therefore an Elan-managed `lean` proxy selects the requested toolchain even though generated source is compiled outside the repository root.

ResearchEvolve then runs:

```bash
lean --version
```

inside that temporary project and requires the detected semantic version to match the frozen version.

Mismatch / missing Lean yields:

```text
environment_error
```

rather than pretending the theorem itself failed.

---

## 8. Kernel gate

A target can reach `formal_verified` only when:

```text
source gate accepted
AND
Lean version matches frozen toolchain
AND
Lean exit code == 0
AND
no Lean error diagnostics
AND
#print axioms output is parseable
AND
all axiom dependencies are allowed
```

A Formalizer or Repairer response has no field that can directly grant this status.

---

## 9. Axiom audit

ResearchEvolve appends:

```lean
#print axioms theoremName
```

and parses the result.

Default v0.6 allowlist:

```text
propext
Classical.choice
Quot.sound
```

Blocked by default:

```text
sorryAx
Lean.trustCompiler
Custom.myAxiom
```

Thus a zero Lean exit status is necessary but not sufficient.

The axiom list is stored in `KernelResult` alongside diagnostics and source SHA-256.

---

## 10. Repair loop

A failed attempt produces a structured result such as:

```json
{
  "passed": false,
  "status": "kernel_rejected",
  "detected_version": "4.30.0",
  "exit_code": 1,
  "diagnostics": [
    {
      "severity": "error",
      "line": 3,
      "column": 8,
      "message": "..."
    }
  ],
  "axioms": [],
  "gate_reason": "lean-exit-nonzero",
  "source_sha256": "..."
}
```

A configured Repairer receives:

```text
Frozen FormalizationSpec
Previous FormalArtifact
KernelResult
Previous kernel history
```

and may only return a replacement theorem body.

```text
FormalArtifact #0
     │
     ├── KernelResult #0: failed
     │
     └── repaired_into
            ▼
      FormalArtifact #1
            │
            └── KernelResult #1: formal_verified
```

Budget exhausted:

```text
repair_exhausted
```

Lean/toolchain unavailable:

```text
environment_error
```

## 11. `formal42` reference demo

```text
examples/formal42/
├── spec.json
├── seeds.json
├── formalizer.py
└── repairer.py
```

Run research:

```bash
research-evolve run \
  --spec examples/formal42/spec.json \
  --evaluator examples/target42/evaluator.py \
  --seeds examples/formal42/seeds.json \
  --conjecturer-command "python examples/conjecture42/conjecturer.py" \
  --workspace .researchevolve/formal42 \
  --islands 2
```

Run v0.5 proof pipeline:

```bash
research-evolve prove \
  --workspace .researchevolve/formal42 \
  --planner-command "python examples/proof42/planner.py" \
  --prover-command "python examples/proof42/prover.py" \
  --verifier-command "python examples/proof42/verifier.py"
```

Run v0.6:

```bash
research-evolve formalize \
  --workspace .researchevolve/formal42 \
  --formalizer-command "python examples/formal42/formalizer.py" \
  --repairer-command "python examples/formal42/repairer.py" \
  --lean-command lean
```

The Formalizer deliberately begins with an ill-typed theorem body:

```lean
by exact 0
```

The real Lean process must reject it. The Repairer returns:

```lean
by exact Nat.zero_le _
```

The second attempt must still pass version checking and `#print axioms` before becoming `formal_verified`.

## 13. Formal manifest

`formal_manifest.json` binds a run to:

- source research fingerprint;
- source generation;
- v0.5 proof manifest fingerprint;
- Formalizer identity;
- Repairer identity;
- kernel command identity;
- target / repair / evidence budgets;
- normalized formal-contract hash.

Changing the statement/predicate mapping or Lean target changes the formal manifest fingerprint.

---

## 14. Stale certificate invalidation

A later counterexample can invalidate the upstream v0.5 proof lineage. On the next formal pass, v0.6 cascades that staleness into:

```text
FormalizationSpec → invalidated
FormalArtifact     → invalidated
KernelResult       → invalidated
```

Historical kernel information is preserved for audit, but the active record no longer says the research conclusion is formally verified.

This distinction is deliberate: Lean may have correctly proved a theorem, while the theorem-to-research-claim mapping has later ceased to be the current valid lineage.

## 16. Security boundary

Lean tactics and elaboration are executable computation. The source gate narrows the v0.6 surface but does not make a local Lean subprocess safe against a determined malicious actor.

For autonomous/untrusted Formalizers:

- isolate Lean in a container / VM / remote worker;
- restrict filesystem, CPU, memory, process count, wall time, and network;
- do not expose model API keys or private evaluator code;
- pin imported libraries and toolchains;
- inspect formal contracts as trusted challenges.

For higher-assurance adversarial proof validation, later versions should add `lean4checker` and ultimately comparator/external checker workflows rather than treating the ordinary compiler invocation as the final security layer.

See [`../SECURITY.md`](../SECURITY.md).

---

## 17. What v0.6 does not solve

v0.6 deliberately does not yet provide:

- automatic correctness of informal→formal translation;
- arbitrary Mathlib project/environment management;
- theorem/library retrieval;
- premise selection;
- large formal lemma search;
- multiple proof assistants;
- distributed Lean workers;
- `lean4checker` / comparator / external-checker validation;
- signed proof certificates.

These are natural next steps.

## 18. Toward qLDPC

A future qLDPC formal pack can progressively freeze and prove claims such as:

```text
circulant algebra definitions
        ↓
Hx / Hz dimensions
        ↓
CSS commutation Hx * Hzᵀ = 0
        ↓
rank-derived k formulas
        ↓
family-specific algebraic invariants
```

v0.6's main contribution is the end-to-end evidence chain:

```text
empirical discovery
→ testable conjecture
→ counterexample attack
→ independent natural-language proof review
→ frozen statement + predicate formal contract
→ real Lean proof term
→ kernel + axiom audit
```

without allowing the generative model to award itself the strongest truth status.
