# ResearchEvolve v0.7 — Frozen Lean Project + Formal Retrieval

v0.7 moves ResearchEvolve formal verification from a generated standalone Lean file into a **content-addressed Lean/Lake project environment**.

The central goal is reproducibility and trust-boundary tightening, not adding another reasoning Agent.

```text
verified_natural_language
        │
        ▼
FormalizationSpec
        │
        ├── exact statement + machine Predicate
        ├── frozen theorem signature/imports/toolchain
        ├── project_fingerprint
        └── premise_index_fingerprint
        │
        ▼
LeanProjectLock (schema v2)
        │
        ├── lean-toolchain
        ├── lakefile.*
        ├── lake-manifest.json
        ├── resolved dependency records
        ├── trusted Lean source hashes
        └── dependency-cache source hashes
        │
        ▼
PremiseIndex → PremiseSelector
        │
        ▼
Formalizer / Repairer
        │ theorem body only
        ▼
materialized frozen Lake project
        │
        ▼
lake build
        │
        ▼
Lean compile + #print axioms
        │
        ▼
leanchecker --fresh
        │
        ▼
formal_verified
```

## Why freeze the whole Lean project?

v0.6 freezes the theorem signature, imports, trusted preamble, toolchain, and axiom policy. But an import such as:

```lean
import MyProject.Definitions
```

is only meaningful relative to the exact local project and dependency state. If `MyProject.Definitions` or a dependency changes while the import name remains the same, the same generated theorem may acquire a different meaning.

v0.7 therefore freezes the project that gives imported names their semantics.

## `LeanProjectLock` schema v2

Create a project lock:

```bash
research-evolve lean-project-lock \
  --project-root path/to/lean-project \
  --source-root . \
  --output project-lock.json
```

The lock fingerprints:

- contents of `lean-toolchain`;
- `lakefile.toml` or `lakefile.lean`;
- `lake-manifest.json` when present;
- normalized resolved package records from the Lake manifest;
- tracked trusted `.lean` sources;
- explicitly selected extra files;
- source-root configuration;
- **actual dependency source bytes under `.lake/packages`**.

Conceptually:

```json
{
  "schema_version": 2,
  "toolchain": "leanprover/lean4:v4.30.0",
  "lakefile": {"path": "lakefile.toml", "sha256": "..."},
  "manifest": {"path": "lake-manifest.json", "sha256": "..."},
  "files": [
    {"path": "MyProject/Definitions.lean", "sha256": "..."}
  ],
  "dependencies": [...],
  "dependency_cache_files": [
    {"path": "mathlib/Mathlib/Algebra/Group/Basic.lean", "sha256": "..."}
  ],
  "fingerprint": "..."
}
```

The lock uses canonical path ordering. A different ordering is rejected rather than silently normalized after loading, so the serialized lock has one reproducible representation.

### Dependency rule

If the Lake project declares dependencies, reproducible mode requires `lake-manifest.json` and a populated `.lake/packages` cache.

The manifest freezes which dependency revisions are expected. `dependency_cache_files` freezes the bytes that will actually be copied into the verification project. This closes the gap where a local dependency checkout could be modified while the manifest revision remained unchanged.

Tracked dependency files reject symlinks. Build artifacts and nested `.git` / `.lake` caches are excluded from the dependency-source hash set.

`--allow-unlocked-dependencies` is only a development escape hatch and should not be used for a research result that claims a reproducible formal environment.

## Project materialization

`LeanProjectEnvironment` never edits the trusted source project. Each verification attempt creates a temporary project and copies:

- the locked toolchain and Lake configuration;
- the exact locked project sources;
- the locked manifest;
- only the exact dependency-cache files listed in the project lock.

The environment is re-captured and fingerprint-checked before materialization. If a trusted source or cached dependency byte changed, the project fails closed before certification.

This is **project isolation, not OS isolation**. A hostile process running as the same operating-system user may still access resources outside its current working directory. Use containers, VMs, remote workers, filesystem restrictions, secret separation, and network controls for adversarial generators.

## Formal premise retrieval

v0.7 introduces:

- `Premise`;
- `PremiseIndex`;
- `PremiseSelector`;
- `PremiseSelection`;
- `formal_retrieval.sqlite3`.

Build an index from a frozen project:

```bash
research-evolve premise-index \
  --project-root path/to/lean-project \
  --project-lock project-lock.json \
  --output premise-index.json
```

Preview retrieval:

```bash
research-evolve premise-search \
  --premise-index premise-index.json \
  --query "rank nonnegative kernel dimension" \
  --module MyProject.Algebra \
  --limit 12
```

The v0.7 baseline selector is deterministic lexical retrieval over frozen local theorem/lemma/def/abbrev declarations. It uses token/IDF and name-overlap scoring.

The scanner is intentionally lightweight; it is not a Lean elaborator and is not meant to be the final Mathlib-scale retrieval solution. False negatives affect proof-generation quality, not the kernel truth gate.

Future selectors can use semantic embeddings, exported declaration databases, theorem dependency graphs, type-directed retrieval, or learned premise selection without changing the `formal_verified` boundary.

## Retrieval is advisory only

The Formalizer/Repairer receives `retrieved_premises`, but retrieval cannot alter:

- theorem signature or name;
- imports;
- trusted definitions/preamble;
- toolchain;
- project fingerprint;
- axiom allowlist.

The default selector only returns declarations from modules already present in `FormalizationSpec.imports`; it does not expand the import surface.

Retrieval mode requires the formal contract to freeze both:

```text
project_fingerprint
premise_index_fingerprint
```

Both must match exactly at runtime. The premise index itself is bound to the same project fingerprint.

## `ProjectLeanKernel`

Project mode verifies this chain:

```text
re-capture and verify project lock
→ exact project_fingerprint check
→ exact toolchain check
→ materialize frozen project
→ lake build
→ compile ResearchEvolveGenerated.lean
→ Lean diagnostics gate
→ #print axioms audit
→ lake env leanchecker --fresh ResearchEvolveGenerated
→ formal_verified
```

The generated `.olean` is placed in the Lake build library path so the checker replays the generated module in the project environment.

`leanchecker --fresh` strengthens environment-integrity checking, but it is not an independently implemented proof assistant and it does not replace OS sandboxing.

## Audit state

v0.7 persists premise decisions in:

```text
formal_retrieval.sqlite3
```

and project verification records in:

```text
formal_project.sqlite3
```

The project audit records:

- project fingerprint;
- `lake build` command, exit code, stdout/stderr;
- generated Lean compile command, exit code, stdout/stderr;
- `leanchecker --fresh` command, exit code, stdout/stderr;
- gate reason and final pass/fail.

Inspect them with:

```bash
research-evolve premise-selections --workspace .researchevolve/run
research-evolve project-checks --workspace .researchevolve/run
```

## Project-mode `formalize`

```bash
research-evolve formalize \
  --workspace .researchevolve/run \
  --formalizer-command "python formalizer.py" \
  --repairer-command "python repairer.py" \
  --project-root path/to/lean-project \
  --project-lock project-lock.json \
  --project-build-target MyProject \
  --premise-index premise-index.json \
  --premise-limit 12
```

If project arguments are omitted, the v0.6 standalone Lean kernel path remains available for small self-contained targets.

## Reference integration: `formal_project42`

The repository contains a dependency-free reference project:

```text
examples/formal_project42/
├── project-lock.json
├── premise-index.json
├── spec.json
├── seeds.json
├── formalizer.py
├── repairer.py
└── lean_project/
    ├── lean-toolchain
    ├── lakefile.toml
    ├── FormalProject42.lean
    └── FormalProject42/
        └── Premises.lean
```

CI exercises the complete chain:

1. regenerate the project lock and require an exact fingerprint match;
2. regenerate the premise index and require an exact fingerprint match;
3. create an empirically supported conjecture;
4. obtain `verified_natural_language` through v0.5;
5. retrieve `FormalProject42.distance_nonnegative`;
6. intentionally emit a bad first Lean proof;
7. make the Repairer refuse to repair unless the premise was actually retrieved;
8. repair using the frozen-project premise;
9. run `lake build`;
10. compile the generated theorem and audit axioms;
11. run `leanchecker --fresh`;
12. require `formal_verified` and inspect the audit databases.

## Exact trust statement

In v0.7, `formal_verified` means:

> A theorem from an exact frozen formal contract was checked inside an exact content-addressed Lean/Lake project, passed the configured source and axiom gates, and passed a fresh Lean checker replay.

It still does **not** automatically establish that the original informal mathematical statement was translated into the correct Lean theorem. The informal-to-formal mapping remains an explicit, auditable research assumption.
