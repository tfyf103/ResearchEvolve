# ResearchEvolve v0.7 — Frozen Lean Project + Formal Retrieval

v0.7 moves formal verification from a single generated Lean file into a **content-addressed Lean/Lake project environment**.

The goal is not to add another reasoning Agent. The goal is to make the formal environment itself reproducible and auditable:

```text
verified_natural_language
        │
        ▼
FormalizationSpec
        │
        ├── exact statement + machine Predicate
        ├── frozen theorem signature/imports/toolchain
        ├── project_fingerprint
        └── premise_index_fingerprint
        │
        ▼
LeanProjectLock
        │
        ├── lean-toolchain
        ├── lakefile.*
        ├── lake-manifest.json
        ├── resolved dependency records
        └── trusted Lean source hashes
        │
        ▼
PremiseIndex → PremiseSelector
        │
        ▼
Formalizer / Repairer
        │ theorem body only
        ▼
materialized frozen Lake project
        │
        ▼
lake build
        │
        ▼
Lean compile + #print axioms
        │
        ▼
leanchecker --fresh
        │
        ▼
formal_verified
```

## 1. Why v0.7 exists

v0.6 freezes the theorem signature, imports, trusted preamble, toolchain, and axiom policy. That prevents a Formalizer from weakening the target directly.

A remaining problem is that an import name is only a name. Consider:

```lean
import MyProject.Definitions
```

If `MyProject.Definitions` changes after the formal contract was written, the same theorem signature may refer to different definitions. A proof could still compile while the research object has silently changed.

v0.7 therefore freezes the **project that gives imports their meaning**.

## 2. `LeanProjectLock`

Create a lock:

```bash
research-evolve lean-project-lock \
  --project-root path/to/lean-project \
  --source-root . \
  --output project-lock.json
```

The lock fingerprints:

- `lean-toolchain` contents;
- `lakefile.toml` or `lakefile.lean`;
- `lake-manifest.json` when present;
- normalized package records from the Lake manifest;
- tracked `.lean` files;
- explicitly requested extra files;
- source-root configuration.

Example conceptual lock:

```json
{
  "toolchain": "leanprover/lean4:v4.30.0",
  "lakefile": {"path": "lakefile.toml", "sha256": "..."},
  "manifest": {"path": "lake-manifest.json", "sha256": "..."},
  "files": [
    {"path": "MyProject/Definitions.lean", "sha256": "..."}
  ],
  "dependencies": [...],
  "fingerprint": "..."
}
```

The `fingerprint` is copied into the relevant frozen formal contract:

```json
{
  "metadata": {
    "project_fingerprint": "..."
  }
}
```

`ProjectLeanKernel` requires an exact match before certification.

### Dependency rule

If a Lake project declares dependencies, v0.7 expects `lake-manifest.json` so resolved revisions are part of the frozen state.

`--allow-unlocked-dependencies` is a development escape hatch for creating a lock without a manifest. It should not be used for reproducible or high-assurance research.

## 3. Isolated project materialization

Project verification does not modify the trusted source tree.

`LeanProjectEnvironment` creates a temporary working copy containing exactly the locked project files. If the project has frozen dependencies, `.lake/packages` is copied into the temporary project.

This avoids silently resolving a different dependency graph during the verification attempt.

It is important to distinguish **project isolation** from **OS isolation**:

- temporary project copy: implemented in v0.7;
- container/VM/network/filesystem containment: deployment responsibility.

A hostile subprocess running as the same OS user is not safely contained merely because its current working directory is temporary.

## 4. Formal retrieval

Large formal projects need premise discovery. v0.7 introduces:

- `Premise`;
- `PremiseIndex`;
- `PremiseSelector`;
- `PremiseSelection`;
- `formal_retrieval.sqlite3`.

Build the index:

```bash
research-evolve premise-index \
  --project-root path/to/lean-project \
  --project-lock project-lock.json \
  --output premise-index.json
```

Preview retrieval:

```bash
research-evolve premise-search \
  --premise-index premise-index.json \
  --query "rank nonnegative kernel dimension" \
  --module MyProject.Algebra \
  --limit 12
```

The default v0.7 selector is deterministic lexical retrieval. It uses exact frozen local source declarations and simple token/IDF scoring.

This design is intentionally conservative. It is a reproducible baseline, not a claim that lexical search is the final Mathlib-scale retrieval system.

Future versions can replace the selector with:

- exported Lean declaration databases;
- semantic embeddings;
- dependency-aware theorem graphs;
- type-directed retrieval;
- learned premise selection;

without changing the kernel truth boundary.

## 5. Retrieval cannot change the target

Retrieval is advisory context only.

The Formalizer receives:

```json
{
  "retrieved_premises": [
    {
      "name": "MyProject.someLemma",
      "module": "MyProject.Algebra",
      "statement": "...",
      "score": 4.21
    }
  ]
}
```

but it still cannot change:

- theorem signature;
- theorem name;
- imports;
- trusted definitions;
- toolchain;
- project fingerprint;
- axiom allowlist.

The default selector only returns premises from modules already present in frozen imports. This sacrifices recall to avoid letting retrieval expand the trusted import surface.

Retrieval mode requires both:

```text
project_fingerprint
premise_index_fingerprint
```

in the formal contract, and both must match exactly.

## 6. `ProjectLeanKernel`

Project mode adds a stronger verification chain:

```text
project lock re-validation
→ exact project fingerprint check
→ exact toolchain check
→ temporary project materialization
→ lake build
→ generated theorem compilation
→ Lean diagnostics gate
→ #print axioms audit
→ leanchecker --fresh generated-module replay
→ formal_verified
```

The generated theorem is written as:

```text
ResearchEvolveGenerated.lean
```

and its `.olean` is placed in the Lake build library path before fresh replay.

### Why `leanchecker --fresh`

The external `lean4checker` project was merged into Lean and archived. In modern Lean 4 toolchains, including the version pinned by this project, the checker is available as:

```bash
lake env leanchecker --fresh ModuleName
```

`--fresh` reconstructs declarations in a clean environment and helps detect environment manipulation such as replacing declarations with alternative same-named ones.

It is not a second independently implemented proof assistant. It is an additional Lean-side replay/integrity gate.

## 7. Project audit journal

v0.7 adds:

```text
formal_project.sqlite3
```

Each project verification records:

- project fingerprint;
- `lake build` command and result;
- generated Lean compile command and result;
- `leanchecker --fresh` command and result;
- stdout/stderr;
- gate reason;
- final pass/fail.

Inspect it with:

```bash
research-evolve project-checks \
  --workspace .researchevolve/run
```

Premise selections are separately inspectable:

```bash
research-evolve premise-selections \
  --workspace .researchevolve/run
```

## 8. Project-mode `formalize`

```bash
research-evolve formalize \
  --workspace .researchevolve/run \
  --formalizer-command "python formalizer.py" \
  --repairer-command "python repairer.py" \
  --project-root path/to/lean-project \
  --project-lock project-lock.json \
  --project-build-target MyProject \
  --premise-index premise-index.json \
  --premise-limit 12
```

If project arguments are omitted, the v0.6 standalone `LeanKernel` path remains available for small self-contained formal targets.

## 9. Reference benchmark: `formal_project42`

The repository contains a dependency-free reference Lake project:

```text
examples/formal_project42/
├── project-lock.json
├── premise-index.json
├── spec.json
├── seeds.json
├── formalizer.py
├── repairer.py
└── lean_project/
    ├── lean-toolchain
    ├── lakefile.toml
    ├── FormalProject42.lean
    └── FormalProject42/
        └── Premises.lean
```

The benchmark intentionally does this:

1. create an empirically supported conjecture;
2. obtain `verified_natural_language` through the v0.5 pipeline;
3. re-generate the project lock in CI and require an exact fingerprint match;
4. re-generate the premise index and require an exact fingerprint match;
5. retrieve `FormalProject42.distance_nonnegative`;
6. make the Formalizer emit a bad first proof;
7. make the Repairer refuse to proceed unless that premise was actually retrieved;
8. repair with the retrieved premise;
9. run Lake build;
10. compile and audit the generated theorem;
11. run `leanchecker --fresh`;
12. require `formal_verified`.

This makes the integration test cover the whole v0.7 chain instead of testing retrieval and formal verification independently.

## 10. Trust statement

In v0.7:

```text
formal_verified
```

means that a theorem from an exact frozen formal contract was checked inside an exact frozen Lean/Lake project, passed the configured source/axiom gates, and passed a `leanchecker --fresh` replay.

It still does **not** automatically establish that the informal mathematical claim was translated into the correct Lean theorem. The informal-to-formal mapping remains an explicit research assumption that must be reviewed.

For hostile AI-generated code, use an OS-level sandbox in addition to ResearchEvolve's logical/project-level gates.
